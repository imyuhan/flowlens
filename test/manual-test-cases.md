# FlowLens ch02 手动测试用例

> 用途：验证 ch02 的 LLM 路径相对 ch01 规则引擎的实际提升。
> 对应验收标准：`docs/ch02/01/spec.md` 的 EA1 / EA3，以及 `docs/ch02/01/checklist.md` 的「分析主路径」一组。

## 使用方法

1. 打开页面 → 点「填入示例」旁边的输入框，粘贴下面任意一条用例
2. 点「开始分析」
3. 先看结果区上方的**来源徽标**，再看结果内容

### ⚠️ 关键前提：先确认徽标

| 徽标 | 含义 | 测试是否有效 |
|---|---|---|
| **「AI 分析」**（青色） | 真的调用了 LLM | ✅ 有效 |
| **「本地规则分析」**（琥珀色） | 降级了，走的是本地规则引擎 | ❌ **无效**，请重跑或检查部署配置 |

**这一条不能跳过。** 本组用例的设计前提是「规则引擎会漏判」，所以降级时你看到 0 个任务是**预期行为**，不能说明 LLM 的好坏。用例 G2-1 尤其容易骗人——降级时你会看到一个 35 分的假任务，看起来像「LLM 判断错了」，实际是根本没调到 LLM。

### 启动方式

```bash
npm run dev:full     # 全栈本地（需 Cloudflare 账号 + 名为 AI 的 Workers AI binding）
```

只跑 `npm run dev` 时接口不存在，页面会自动降级——可用于验证降级路径，但**不能**用于本组用例。

## 测试组 1：语义识别（EA1）★ 本轮核心主张

规则引擎的匹配是全字**子串包含**，改写一个词就能绕开它。以下输入经实测在规则引擎下**全部返回 0 个任务**；LLM 路径应能识别出任务。

### G1-1 数据搬运

```
我天天盯着销售表，把数字抄进周报，一个月下来特别费时间，眼睛都花了。
```

- 规则引擎实测：**0 个任务**
- 期望 LLM：「天天」≈ 每日重复、「抄进周报」≈ 手工数据搬运 → 1 个可自动化任务
- 漏判原因：「天天」不含「每天」；「抄」不命中「整理 / 复制 / 粘贴」

### G1-2 重复应答

```
客户来消息问价格，我得挨个回，同一句话要打三遍才说得清楚。
```

- 规则引擎实测：**0 个任务**
- 期望 LLM：高频重复的应答动作 → 1 个可自动化任务
- 漏判原因：「回」不命中「回复」；「挨个」「打三遍」不含任何耗时词

### G1-3 手工排班

```
店里排班全靠我拍脑袋，谁有空谁上，改一次要挨个问一圈。
```

- 规则引擎实测：**0 个任务**
- 期望 LLM：手工、频繁调整的排班 → 1 个可自动化任务
- 漏判原因：全句不含任何三维度词典词

### G1-4 混合场景（识别 + 排除）

```
每周一我要把上周的客服记录翻一遍，把骂人的挑出来单独发给主管；另外我最近在学吉他，周末会练两小时。
```

- 规则引擎实测：**0 个任务**
- 期望 LLM：翻记录挑异常 → 1 个可自动化任务；**学吉他应被排除**

这条最微妙，值得记下规则引擎为何失手：句子确实命中了「每周」（权重 3），重复性得 60 分，但其余两个维度都是 0，加权后
`60 × 0.35 + 0 × 0.4 + 0 × 0.25 = 21`，低于 25 的阈值 —— 于是**连同后面的「学吉他」一起被整段丢弃**。这是规则引擎「维度割裂 + 整段二元取舍」的典型失败。

## 测试组 2：精度对照 ★ 最能说明问题

### G2-1 含触发词的闲聊

```
每天早上我都会定期想想人生规划，反复思考怎样提升自己。
```

| | 规则引擎 | 期望 LLM |
|---|---|---|
| 任务数 | **1 个（误判）** | **0 个** |
| 分数 | 35 分 | — |
| 命中词 | `每天`、`定期`、`反复` | — |

规则引擎在这里产出了一个 35 分的**假任务**——可这压根不是工作流程。这正是 ch01 README 写的那条局限的活标本：

> *It may … flag a segment purely because it contains a trigger word.*

**这组与测试组 1 合起来才是完整的证据**：LLM 在 G1-* 上应「多出任务」，在 G2-1 上应「少了任务」。只有两个方向都成立，ch02 的价值才被证明。

## 测试组 3：理由质量（EA3）

### G3-1 规则明确的条件分支

```
如果订单金额超过 5000 块，就走大客户流程，否则按普通流程处理。
```

- 规则引擎实测：1 个任务，25 分（刚好过阈值）
- 两条路径**都该**给出任务——差异在「判定依据」的呈现：
  - 规则路径：显示 `#如果`、`#否则`、`#超过` 这类命中词标签
  - LLM 路径：显示「判定依据」区块，内容应是语义理由，如「金额阈值判断，可写成规则」
- 看点：**同样数量的任务，理由的可读性差异**

## 测试组 4：边界

### G4-1 纯闲聊

```
今天天气不错，阳光明媚，适合出去散散步晒晒太阳。
```

- 规则引擎实测：0 个任务
- 期望：两条路径都显示「未识别到可自动化任务」

### G4-2 超长输入（对应 spec F6）

生成 2070 字后粘贴进输入框：

```bash
node -e "process.stdout.write('每天整理销售数据，把表格复制粘贴到周报里；'.repeat(90))"
```

- 期望：提示输入过长，**且不消耗 LLM 额度**
- 验证不消耗额度：服务端在调用模型之前就返回了（`functions/api/analyze.ts` 的长度校验位于 `env.AI.run` 之前）

### G4-3 过短输入

```
整理数据
```

- 期望：就地提示「至少输入 10 个字」，**不发出任何网络请求**
- 验证方式：打开浏览器开发者工具的 Network 面板，点「开始分析」，确认无请求

## 附录：本文档中「规则引擎实测」数据的来源

数据于 2026-09-10 通过直接调用 `lib/analyzer.ts` 的 `analyze()` 取得，非估算。复现方式：

```bash
cat > scripts/tmp-check.ts <<'EOF'
import { analyze } from "../lib/analyzer";
const r = analyze("每天早上我都会定期想想人生规划，反复思考怎样提升自己。");
console.log(r.tasks.length, "个任务", r.tasks[0]?.priorityScore, "分", r.tasks[0]?.matchedKeywords);
EOF
npx tsx scripts/tmp-check.ts
rm scripts/tmp-check.ts
```

实测输出：

```
1 个任务 35 分 [ '每天', '定期', '反复' ]
```

> ⚠️ 别用 `npx tsx -e "..."` —— 实测它会进入 REPL 等待输入、不返回（本次验证中卡到 120 秒超时）。请用上面的临时文件方式。

词典内容与权重定义见 `docs/design-decisions.md` §4；阈值 25 见 §5.3。
